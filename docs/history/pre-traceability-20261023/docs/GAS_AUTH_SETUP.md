## 認証方式と権限

全データ取得・更新は `POST` の JSON 本文 `{ "action": "...", "token": "...", ... }` で送信します。`GET` は稼働確認メッセージだけを返します。アクセスキーをURL、ソースコード、Git、共有ドキュメント、ログへ記載しないでください。フロントエンドは実接続のキーをタブの `sessionStorage` に保持します。ログアウトでクライアントから削除しても、キー自体の失効にはサーバー設定の削除または `active: false` の設定が必要です。

GASは毎回、キーのSHA-256を計算し、Script Propertiesの `AUTH_USERS_JSON` と照合します。Googleの個人アカウントへのログインを検証する方式ではありません。管理者が個人へ安全に配布する、長いランダムなアクセスキーによる認証です。キーは保護者ごと・管理者ごとに別々に発行してください。デモモードの操作やブラウザー内の役割値は、GASの認証・認可には使用しません。

| サーバーで確認する操作 | 管理者 `admin` | 保護者 `parent` |
| --- | --- | --- |
| `login` | 自分のID・名前・役割・紐付けを返す | 同左 |
| `getStudents` / `getRides` | 全件 | `studentIds` に登録した生徒の行だけ |
| `createReservation` / `cancelReservation` | 全生徒 | 登録済み生徒の範囲だけ |
| `getPortalInvitations` | 有効な家庭の利用者ID・表示名・個別入口IDのみ取得 | 拒否 |
| `createStudent` / `addTickets` / `completeRide` | 許可 | 拒否 |
| `initSpreadsheet` | スクリプト編集者がエディタで手動実行 | Web APIから実行不可 |

保護者の `studentId` 改変、`role: "admin"`、任意の氏名・予約者・カレンダーID送信によって権限は変わりません。取消は送迎IDで保存行を取得し、その生徒IDとカレンダーIDを使います。日時だけが一致する別予約は取り消しません。

## 個別キーとハッシュの作成

次のコマンドは運用管理者が安全なローカル端末で実行する例です。このリポジトリには実キーも共通初期パスワードもありません。実行結果をCI・チャット・録画等に残さないでください。キーは32バイトの乱数から作成します。人が決めた短いパスワードをSHA-256化して代用しないでください。

```powershell
node -e "const c=require('node:crypto'); const accessKey=c.randomBytes(32).toString('base64url'); const sha256=c.createHash('sha256').update(accessKey,'utf8').digest('hex'); console.log(JSON.stringify({accessKey,sha256},null,2));"
```

既存のキーを再ハッシュする必要があるときは、コマンド履歴へキー本文を書かず、標準入力から渡します。以下はPowerShellの入力例です。

```powershell
$taxiAccessKey = Read-Host 'Access key' -MaskInput
$taxiAccessKey | node -e "let s=''; process.stdin.setEncoding('utf8'); process.stdin.on('data',v=>s+=v); process.stdin.on('end',()=>console.log(require('node:crypto').createHash('sha256').update(s.trimEnd(),'utf8').digest('hex')));"
Remove-Variable taxiAccessKey
```

`-MaskInput` は対応するPowerShell 7で使用します。生キーは承認済みの安全な個別経路で対象者へ渡し、管理者は失効・再発行できる台帳を管理します。画面写真や共用メッセージへ貼り付けない運用にしてください。

## Script Propertiesの登録

Apps Scriptの「プロジェクトの設定」→「スクリプト プロパティ」にキー `AUTH_USERS_JSON` を追加し、次の形のJSONを値にします。`<...>` はすべて説明用の置換箇所で、このままではログインできません。ハッシュは上記コマンドの64桁・小文字の16進数です。生徒IDは既存の「生徒台帳」A列と完全一致させます。

```json
{
  "<ADMIN_KEY_SHA256_HEX>": {
    "id": "admin-01",
    "name": "<管理者表示名>",
    "role": "admin",
    "studentIds": []
  },
  "<PARENT_A_KEY_SHA256_HEX>": {
    "id": "parent-01",
    "name": "<保護者A表示名>",
    "role": "parent",
    "studentIds": ["<家庭Aの生徒ID>"],
    "publicEntryId": "<家庭A用のランダムUUID-v4>"
  },
  "<PARENT_B_KEY_SHA256_HEX>": {
    "id": "parent-02",
    "name": "<保護者B表示名>",
    "role": "parent",
    "studentIds": ["<家庭Bの生徒ID1>", "<家庭Bの生徒ID2>"],
    "publicEntryId": "<家庭B用の別ランダムUUID-v4>"
  }
}
```

兄弟姉妹は配列へ追加します。複数の保護者が同じ生徒を扱う場合も、それぞれ別キー・別利用者IDで同じ生徒IDへ紐付けます。紐付けのない保護者は `studentIds: []` とし、データは0件になります。新規生徒の作成だけでは保護者への紐付けは増えません。管理者が生徒IDを確認して個別に更新します。

未設定・空設定・JSON破損・不正な利用者設定では認証を許可しません。権限の追加・削除は次のリクエストからサーバーで判定します。スクリプト編集者は認証設定と実データを管理できるため、プロジェクト・スプレッドシート・カレンダーの共有権限も必要な管理者へ限定してください。保護者へスプレッドシートを直接共有する必要はありません。

Script Propertiesの設定方法は[Google公式Properties Serviceガイド](https://developers.google.com/apps-script/guides/properties)、ハッシュ計算は[Google公式Utilitiesリファレンス](https://developers.google.com/apps-script/reference/utilities/utilities#computedigestalgorithm,-value,-charset)を参照できます。

8. 管理者・家庭A・家庭Bを独立したブラウザープロファイルで開き、下記の実環境確認を行います。

Webアプリの配備・実行ユーザー設定は[Google公式Web Appsガイド](https://developers.google.com/apps-script/guides/web)を参照してください。

## 失効・変更

- 紛失・漏えい・退会時は、そのキーのハッシュ項目を `AUTH_USERS_JSON` から削除して保存します。古いキーによる次のリクエストは拒否されます。管理者が発行した新しいキーとハッシュを登録し、安全な経路で本人へ再配布します。
- 生徒の紐付けや管理者権限を変更した場合は、独立した保護者セッションから再取得し、以前の対象へ操作できないことを確認します。ブラウザー側の表示だけで確認を終えないでください。
- 表示名変更でも `id` は本人を表す安定した値を保ちます。利用者ID・ハッシュ・紐付けの管理記録に生キーを書かないでください。

## 入力・再試行・終端状態

| 操作 | 入力・確定する動作 |
| --- | --- |
| 予約 | 必須 `rideId` は操作ごとにUUID等で生成し、応答不明時も同一ID・同一内容で再送。既存IDなら既存予約を返し、予定を増やさない。内容違いは `ID_CONFLICT` |
| チケット追加 | 必須 `purchaseId` は操作ごとに生成し再試行で保持。枚数はJSON数値の整数1〜100、金額は0以上の安全な整数。購入ID再送では加算しない |
| 生徒作成 | クライアントで安定した `id` を生成して再試行で保持することを推奨。省略時はサーバーでUUIDを生成するため、応答不明時にIDを変えて再送しない。初期残高は0以上の安全な整数 |
| 完了 | 保存済み送迎区分が片道なら1枚、往復なら2枚。`consumeTickets` を送る場合はその枚数と一致が必要。`completed` の再実行は `consumedTickets: 0` と現在残高を返す |
| 取消・状態 | `scheduled` だけを完了／取消できる。`cancelled` の完了は拒否。同じ取消は変更なしで成功。取消にカレンダーIDや日時を指定しても操作対象には使わない |
| 残高不足 | 不足時は更新せず `INSUFFICIENT_TICKETS`。残高0へ丸めて消化成功とはしない。この保守的な暫定挙動は残高不足の業務運用合意とは別に扱う |

負数、小数、`null`、数値文字列、非有限値、JavaScriptの安全整数範囲外は拒否します。新しい操作IDで再送すると新規操作になるため、応答不明時は同じIDを維持してください。

## `PENDING_MUTATION_JSON` が残ったとき

全データ操作はScript Lock内で実行します。変更前に `PENDING_MUTATION_JSON` へ操作名・対象ID・開始時刻を書き、正常終了してSheetsの書き込みを反映した後に消します。途中の例外は書き込みを逆順に戻します。補償に失敗した場合、実行が途中で終了した場合、カレンダー操作の結果が不明な場合はマーカーを残し、後続のデータ取得・更新を `RECONCILIATION_REQUIRED` で停止します。ログインとGET稼働確認は可能です。

Script Lockと `SpreadsheetApp.flush()` の使い方は[Google公式Lockリファレンス](https://developers.google.com/apps-script/reference/lock/lock)に基づきます。Sheets、Calendar、Propertiesをまとめて確定／取消するトランザクションはありません。カレンダー削除後に同じイベントIDを復元することもできません。この仕組みは未確定の結果を成功と表示したり、自動再送で重複させたりしないための保護です。Properties自体が利用不能な場合、マーカーの再保存まで保証できないため、エラーの出た対象操作も照合してください。

管理者は以下の順序で復旧します。APIからマーカーだけを解除する機能は設けていません。

1. 利用者の更新を一時停止し、Apps Scriptの実行状況で同じ処理がまだ動いていないことを確認します。スプレッドシート・カレンダー・設定と、対象処理前のバックアップ／実行記録を確保します。
2. Script Propertiesの `PENDING_MUTATION_JSON` の `action` / `key` / `startedAt` を確認します。マーカーにはアクセスキーや生徒の個人情報を保存しません。対象IDから生徒行、送迎行、購入行、カレンダーを照合します。
3. `completeRide` は残高・送迎状態・完了日時の3点を照合します。完了済みなら必要枚数が一度だけ減っている状態へ統一し、未完了へ戻すなら処理前残高と予約状態へ戻します。時刻前後の他の購入・完了を含めて確認し、残高を推測で補正しないでください。
4. `addTickets` は同じ購入IDの履歴が1行だけ存在し、その追加が残高へ一度だけ反映されたか確認します。反映前へ戻す場合は履歴と残高の両方を復元します。`createStudent` は同じ生徒IDの重複・不完全行を確認します。
5. `createReservation` は送迎IDの行と実カレンダーを確認します。カレンダー作成後に応答を失うと予定IDが行に記録されていないことがあります。対象日時・生徒・作成時刻を確認し、該当の予定のみを特定して補正します。同時刻の別予約を日時だけで削除しないでください。必要なら予定IDを正しい送迎行へ保存し、予定と行を一対一にします。
6. `cancelReservation` は既定カレンダーの保存イベントIDを調べます。イベントが削除済みなら対象の送迎行も取消済みに整えます。イベントが残る場合は、取消を完了させるか予約状態へ戻すかを決め、行と予定の整合を確認します。削除済み予定を再作成する場合は新IDを行へ正しく保存します。
7. 対象データの整合が確認できた後に限り、管理者が `PENDING_MUTATION_JSON` を削除します。補正内容・担当・日時を記録し、同じ操作IDの再送で残高や行・予定が増えないことを確認して受付を再開します。

このロックは同じApps Scriptプロジェクト内の処理に効きます。シートの直接編集や、別プロジェクトの書き込みは制御しません。照合中や通常運用中に別経路で同じ台帳を更新しない運用が必要です。

現在の検証GASは検証用コピーに紐付いています。コピー元の台帳とは自動同期しません。台帳名・URLは [検証環境の台帳一覧](TEST_ENVIRONMENT_ACCESS.md#検証用台帳と元の台帳) を参照してください。元の台帳を本番接続先とみなさず、本番環境は別途準備します。

`sheet_()` は紐付くスプレッドシートの正確なタブ名「生徒台帳」「送迎予定履歴」「チケット購入履歴」を参照します。`AT23生成証跡_` のタブは読み取り対象ではありません。`getStudents`・`getRides` が取得したデータを画面に保持し、リアルタイム監視・定期取得・直接編集用の `onEdit` 同期はありません。直接編集を表示するには保存後に画面を再読み込みします。

`ride_()` は送迎予定履歴C列の生徒名をその予約の表示に使います。C列のみの修正は生徒台帳・保護者名・他の予約を変更しません。直接編集ではAPIのロック・更新ガード・カレンダー連携・チケット計算・関連履歴更新を経由しないため、[保守時の直接編集手順](TEST_ENVIRONMENT_ACCESS.md#台帳を直接編集した後の反映) に沿ってバックアップ・同時操作停止・整合確認を行います。


## ポータル要求の追加契約

新フロントはPOST本文に `portalRole` と、個別URLの場合は `entryId` を送ります。GASは本人のサーバー役割と個別IDを照合し、役割違いを `PORTAL_MISMATCH`、個別ID違いを `ENTRY_REVOKED` で拒否します。旧クライアントとの互換のため両項目の省略自体は許容しますが、キーによる既存の家庭・管理者権限検証は常に行います。`publicEntryId` は認証キーとは別のUUID v4で、有効な利用者間で一意にします。`active: false` は本人キーを無効化します。詳細は[画面分離・個別URL運用の変更仕様](PORTAL_SEPARATION.md)を参照してください。
