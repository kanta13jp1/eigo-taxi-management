## 権限設計

検証専用の永続ロール `reviewer` を用意し、同じGoogle UIDから家庭用・管理者用の固定URLを本人が選ぶ方式で、各段階の開発者による役割変更を取り除ける。APIの業務ロールは入口に応じた `parent` または `admin`、制限はサーバー生成の `reviewOnly: true` とサーバー登録の `studentIds` で表す。通常の利用者は既存の単一ロールのまま。

| 境界 | 採用条件・失敗時の確認 |
| --- | --- |
| Google本人・初回の登録 | `authenticateGoogle_` が検証したFirebase Google UIDのみを受け入れる。事前登録メールの有効性、実行環境、入口、家庭IDを確かめてからロック内でUIDへ結合。誤った入口や他人のメール、失効したアカウントで結合・台帳変更がない。legacyキーはreviewerに利用できない。 |
| 検証環境 | `ACCEPTANCE_REVIEW_SPREADSHEET_ID` と実行プロジェクトに紐付いた台帳IDの完全一致が必須。空値、別台帳、未接続では拒否。端末・URL・POSTから台帳IDを上書きできないこと。通常の管理者だけがreviewerを登録し、reviewer自身は管理者人数に数えない。 |
| 偽造・失効 | `portalRole` は許された2ビューの選択にのみ用いる。POSTの `role`、`studentIds`、`reviewOnly` は信頼しない。待機後に同じGoogle UIDの**現在の**行を読み直し、有効状態・ロール・割当・台帳IDを再検査。異なるUIDや同じアプリ用IDを持つ別の行への差し替え、停止、割当解除、ゲート解除の後は更新件数0。 |
| 閲覧・更新 | 管理者入口のreviewerも両一覧を割当生徒に絞る。取消・完了は送迎行に保存された生徒IDで判定。予約・購入の既存IDへの再送や衝突についても、元の台帳行の生徒IDを確認してから結果を返す。片道/往復の消費枚数はサーバーの確定区分で決める。 |
| 教室全体の操作 | 管理者入口のreviewerも生徒作成、招待・家庭用URL一覧、利用者一覧・編集・削除をサーバーで拒否。設定・アカウント管理のナビと画面自体も出さない。通常の管理者・保護者の既存操作は回帰テスト対象。 |
| Googleカレンダー | カレンダー閲覧ACLはアプリの生徒別認可から独立する。共有中の専用カレンダーには顧客に閲覧させてよい架空の予定だけを載せる。業務予定が混在するカレンダーを丸ごと共有して、生徒別に非表示となる想定は成立しない。 |

**架空生徒の追加許可リスト**　現行の検証台帳が架空データ専用であることを運用で確認し、登録済み `studentIds` が対象1名だけと保存後に照合できれば、今回のために第2のScript Propertyを設ける必要はない。小林さん本人が他の3名を選ぶPOSTを作ってもサーバーが拒否することを確認する。厳密な仕様表現は「指定した検証台帳のうち、管理者が割り当てた検証生徒だけ」。管理者による別生徒の誤指定まで禁止する場合、あるいは今後の混在台帳でも架空性を機械的に保証したい場合にのみ、独立した適格生徒リスト・レコード属性が必要になる。

## 日付と中断再開

- 開始前に開発者が専用の1生徒・残5枚・固定日時の片道/往復2行 `scheduled` を一度だけ用意し、専用カレンダーのイベントを照合する。検証用の架空の模擬実績に実施済みの印を付ける。CUST-04は「送迎スケジュール一覧」→「すべてのステータス」から、固定の日付・時刻・区分・場所で該当行を識別する。`TeacherDashboard` の全履歴タブの完了ボタンは当日タブと同じ `onCompleteRide` を呼び、GASの `completeRide_` に日付条件はない。備考や予約IDはこの一覧には表示されないので、目印は乗車場所にも付ける。
- CUST-02/03で本人が試す予約Cを、完了用A/Bと違う時刻・場所・区分表示で特定する。最初から準備した2件が家庭画面の予約中に含まれるため、CUST-02は既存2件から1件増、CUST-03はCの取消で元の2件に戻る。取消済みの過去履歴は保持される。
- 中断時は共有表にCUST番号・最終観測・予約ID・時刻を控える。再開時は未記入項目を見た後、**必ず台帳と画面の実状態を照合**する。両方が予約中で残5枚なら片道から、片道完了で残4枚なら往復だけ、両方完了で残2枚なら案内を記録して追加。残12枚なら追加済みとして再購入を避け、家庭側の案内消失と両入口のログアウト確認に進む。以前の観測を記録し忘れたときは、本人が見ていない値を過去の結果として記入しない。
- 完了・取消の再送は同じ予約IDで冪等。新規予約と追加は`src/services/api.ts`の `mutation` が同じタブの `sessionStorage` に未完了操作IDを保持する方式で、タブ終了・別端末・成功後の再押下は別IDになり得る。「どの端末からも再度ボタンを押して安全」と約束するなら、reviewer限定で実施回・生徒・段階ごとの永続的な予約／購入IDを使い、同時の2要求でも1件しか記録されないテストが必要。正常操作1回と状態照合による再開の仕様なら、自動リセットや全顧客用DBの追加は不要。予約の通信異常後も再送前に予約/カレンダーの状態を照合する。
- `PENDING_MUTATION_JSON` による保護中や残数と予約状態が矛盾するときは、「未確認」で止める。通常の中断は本人だけで続けられる。障害の照合中まで本人が書込み保護を解除できる方式にはしない。小林さん本人の試験を開発者が代行してPASSにしない。
